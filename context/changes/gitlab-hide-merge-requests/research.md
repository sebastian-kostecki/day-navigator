# Research: hide a GitLab merge request (S-07, MS-33)

Paths are relative to the worktree root. Line numbers are from commit 76cd680 (develop, wave 2 merged); a `~` marks an approximate line. Source: reading code only; no build, no test run, no real `glab` call (work data rule).

## Decisions fixed by the user (binding, not re-opened)

1. Hiding covers both assigned MRs and MRs in "Do review" (S-06).
2. An MR comes back as "Zmienione" ONLY after a state change or a comment by someone else (the FR-003 rule, `context/foundation/prd.md:126`). Approvals, commits and pipelines do NOT bring it back.
3. MR comment data comes through a NEW read-only `glab api` call: a new `CliCall` variant with fixed arguments, covered by the read-only guard test, plus fake-cli support in `src-tauri/src/bin/fake_cli.rs`.
4. No migration; GitLab issue hiding (`hidden_issues` table) keeps its behaviour.
5. AGENTS.md app-data list: hidden-item snapshots now include GitLab merge requests (by host and global id); still no title, URL, comment text or login.
6. An MR both assigned and in "Do review" behaves as one item for hiding (one record, hidden from both places).

## Short answer

- **No migration is needed.** `hidden_items` (v15, `src-tauri/src/store/schema.rs:306-327`) accepts `source='gitlab'`, `kind='mergeRequest'`, `scope` = host, `item_id` = global MR id, and requires `project_id`/`iid` for gitlab rows (`CHECK ((source = 'gitlab') = (project_id IS NOT NULL))`, `schema.rs:324`). The store ops in `src-tauri/src/hidden_issues/items.rs` (`hide_item`, `unhide_item`, `dismiss_item`, `list_items`, `apply_items_round`) are parameterised by `HiddenSource`/`HiddenKind`, and `HiddenSource::Gitlab` / `HiddenKind::MergeRequest` already exist (`items.rs:15-55`). The rules (`plan_round`, `comment_verdict`, `needs_comment_check`) are generic over `HideRecord`/`HideItem` (`rules.rs:48-72`), and `HideRecord` is already implemented for `HiddenItemRecord` (`rules.rs:128-150`). The one rules gap: `impl HideItem for GitlabItem` returns scoped labels (`rules.rs:74-83`), which is right for issues and not for MRs (section 6).
- **One new call**: `glab api projects/<project_id>/merge_requests/<iid>/notes?sort=desc&order_by=created_at&per_page=100 --paginate --hostname <host>`, a sibling of the issue notes call. The notes parser (`src-tauri/src/gitlab/notes.rs`) is reusable unchanged (inference, see section 4).
- **The one real design question** is what "state change" means for an MR (section 6): the app lists only `state=opened` MRs, so a merged or closed MR just leaves the list. This needs an owner choice; a recommended default is given.

## 1. How GitLab MRs are fetched today

- `fetch_assigned` (`src-tauri/src/gitlab/fetch.rs:16-47`) runs three calls in order, the first failure ends the round: `CliCall::GlabAssignedMergeRequests`, `GlabAssignedIssues`, `GlabReviewMergeRequests`. The review list is then split against the assigned list by `split_review_requests` (`src-tauri/src/gitlab/mod.rs:108-128`).
- Endpoints (`src-tauri/src/cli/mod.rs:208-221`): `ASSIGNED_MRS_ENDPOINT` = `merge_requests?scope=assigned_to_me&state=opened&with_labels_details=true&per_page=100`; `REVIEW_MRS_ENDPOINT` = same with `scope=reviews_for_me`; with a configured user the `...assignee_username=` / `...reviewer_username=` prefixes. Argument list `api <endpoint> --paginate --hostname <host>` (`cli/mod.rs:223-240`). Both lists are `state=opened` only.
- Fields per item (`GitlabItem`, `gitlab/mod.rs:68-105`; raw side `RawItem`, `gitlab/mod.rs:311-332`): `id` (global id, the key of a hide record), `project_id` and `iid` (Rust-only, `#[serde(skip)]`, documented as "builds the notes call"), `reference` (`references.full`), `title`, `web_url`, `updated_at` (RFC 3339 text), `labels`, `draft`, `milestone`, `changed`, `is_new`, `hidden_at_ms`, `review_requested`. `state` is parsed into `RawItem` only for the recently-closed parser (`gitlab/mod.rs:325-331`) and is not kept on `GitlabItem`. `build_item` rejects a zero id/project_id/iid (`gitlab/mod.rs:370-374`), so a hide record or notes endpoint is never built from zero.
- Result shape `AssignedItems` (`gitlab/mod.rs:139-149`): `merge_requests` (assigned), `issues` (visible), `hidden_issues`, `review_requests` (review-only MRs). The review list is not hidable today; S-06's plan defers it to S-07 (`context/archive/2026-11-27-gitlab-review-requests/plan.md:80`).
- Dedupe between assigned and review: `split_review_requests` flags every assigned MR that also awaits review (`review_requested = true`) and returns only the review-only items, each flagged; the first occurrence of an id wins (`gitlab/mod.rs:104-128`). After it the two lists are disjoint by id: an MR sits in exactly one of `merge_requests` / `review_requests`, so one global id keys one hide record whatever the section.
- Id spaces: GitLab issue and MR global ids come from separate tables and can collide (inference; the code already keys seen records by `(kind, id)`, `src-tauri/src/new_assignments/mod.rs:60-70`). Every lookup by id must check the kind too, as `act_on_issue` does (`gitlab_refresh.rs:162-166`).
- "Recently closed" section: `GlabRecentlyClosedMergeRequests` (`state=all&updated_after=...`), assigned MRs only, built when `gitlabFilter.closedDays` is set; `closing_time` reads `state` `merged`/`closed` with `merged_at`/`closed_at` (`gitlab/mod.rs:~420-446`). Hiding does not touch it.

## 2. How GitHub hide/resurface (S-01) uses `hidden_items` and the generic rules

- Plan with the storage and rules decisions: `context/archive/2026-11-27-github-hide-resurface/plan.md` ("Team Questions" 1 and 2: `hidden_items` keyed `(source, scope, kind, item_id)`; nullable `project_id`/`iid` "give S-07 its MR notes call"; `status_fingerprint` JSON "holds S-07's scoped labels").
- Store (`hidden_issues/items.rs`): `hide_item` stores the fingerprint, baseline `updated_at`, `settle_after_ms = now + SETTLE_MS` and `hidden_at_ms`; `unhide_item`/`dismiss_item` delete by key (hidden vs marked); `apply_items_round` applies a round's transitions per scope in one write, each guarded by `hidden_at_ms`, and prunes stale rows of non-active scopes.
- Rules (`hidden_issues/rules.rs`): `plan_round` per record: no listed item -> `MarkAbsent`, or `Prune` after `PRUNE_AFTER_MS` (30 days); listed and already marked -> `ClearAbsent` if needed; hidden -> reason `Status` if the fingerprint differs, else `Comment` if the verdict is `NewFromOthers`, else `Returned` if the record was absent, else `AdvanceBaseline` after a `NothingNew` check (with one settling re-check `SETTLE_MS` = 2 min when `updated_at` had moved). `needs_comment_check` = hidden and (`updated_at` > baseline or settle due). A comment counts when `counts` (not a system note), `created_at` > baseline and its author differs from the user (ASCII case-insensitive); a missing author is someone else; with no known user every author counts (`rules.rs:~245-268`).
- GitHub round (`hidden_issues/github_round.rs`): `check_github_round` (no lock) reads records, picks due items, fetches the login once with `gh api user` (a failed login = every due check failed), then one comments call per due item, stopping on Unavailable/LoggedOut/ToolMissing and resuming after the stopped record next round (`github_round.rs:~95-200`); `commit_github_round` plans per repo and applies one write. Commands `hide_github_issue`, `unhide_github_issue`, `dismiss_github_change` take the issue `reference` and resolve it against the kept full list (`hidden_issues/commands.rs:~96-178`).
- **How "someone other than the user" is known**: GitHub calls `gh api user` per round. GitLab has no such call; the user is the optional `gitlab.user` setting (`GitlabConfig.user`), passed as `config.user.as_ref().map(GitlabUser::as_str)` (`hidden_issues/round.rs:~118-121`). Without it the snapshot has `own_comments_known = false` and the view shows a warning notice (`src/gitlab/GitlabView.tsx:740-744`). MR hiding inherits exactly this.

## 4. `glab api` for MR notes, and the reuse pattern

- Existing issue notes call: `CliCall::GlabIssueNotes(GitlabHost, IssueRef)`, args `api projects/<project_id>/issues/<iid>/notes?sort=desc&order_by=created_at&per_page=100 --paginate --hostname <host>` (`cli/mod.rs:349-364`); `IssueRef { project_id, iid }` (`cli/mod.rs:~299`); `fetch_issue_notes` -> `parse_notes` (`gitlab/fetch.rs:~128-137`, `gitlab/notes.rs`). `parse_notes` reads only `author.username`, `system` and `created_at`; the note body is never deserialized (leak test at the bottom of `notes.rs`).
- GitLab's REST endpoint for MR notes is `GET /projects/:id/merge_requests/:merge_request_iid/notes` with the same `sort`, `order_by` (`created_at` | `updated_at`) and pagination, and note objects with the same `author`, `system`, `created_at` fields (from GitLab's public API documentation; not verified against a live server, and no real call may be made with work data). Inference: `parse_notes` works unchanged. `system: true` notes are the generated ones (merged, closed, reopened, approved, label changes, "marked as draft"); user notes are `system: false`; diff-thread replies are ordinary notes. So "comment by someone else" = `counts = !system`, as for issues.
- **Proposed variant**: `CliCall::GlabMergeRequestNotes(GitlabHost, IssueRef)` (reuse `IssueRef`, or add an `MrRef` newtype), `name()` = `glab:mr-notes`, doc "GET of one merge request's notes, newest first (read-only)". Args `api projects/<D>/merge_requests/<D>/notes?sort=desc&order_by=created_at&per_page=100 --paginate --hostname <host>`. Constants next to `ISSUE_NOTES_*` (`cli/mod.rs:349-351`) or a parameterised builder.
- **Guard test changes** (test module in `cli/mod.rs`): `VARIANT_COUNT` 13 -> 14 and `EXAMPLE_COUNT` 18 -> 19 (if no other slice adds a call), an `ordinal` arm (exhaustive, no `_` arm, `:~548-565`) and a `seen` array entry, the variant in the "ALL must stay parameterless" list (`:~597-610`), and `notes_endpoint_allowed` (`:~705-715`) must accept exactly `projects/<D>/merge_requests/<D>/notes?<same suffix>` as a second shape (it currently splits on `/issues/`); near-miss tests (`merge_requests/0/notes`, leading zero, extra query, `/notes/<id>`, `-X`, `projects//merge_requests/...`). `check_read_only` already accepts any `api <endpoint> --paginate --hostname <host>` whose endpoint passes `endpoint_allowed`, so only that predicate changes. The variant is not added to `CliCall::ALL` (not parameterless).
- **fake-cli** (`src-tauri/src/bin/fake_cli.rs`): `Endpoint::Notes{project_id,iid}` and `parse_notes_endpoint` (`:55-71`) know only `/issues/`; add an MR-notes endpoint (a `kind` field or a new variant) and a branch in `endpoint()` (`:73-100`), then serve MR notes from `gitlab_notes_body` for the existing `gitlab-notes-*` scenarios (`:347-390`, dispatch `:746-753`) with a fixed invented project/iid for MRs, reusing `FAKE_CLI_NOTES_LOG` / `FAKE_CLI_CALL_LOG` call logging (`:392-465`) to count calls. Invented data only.
- Cost note: an MR's `updated_at` moves on pushes, pipelines and approvals, so a hidden MR with CI activity triggers one notes call per `updated_at` movement (`needs_comment_check`), after which the baseline advances (`AdvanceBaseline`). Same rule as issues, likely more frequent for MRs; calls stop after the first Unavailable/LoggedOut/ToolMissing (`stops_round`, `round.rs:~58-64`). The per-round volume was not measured.

## 6. What "state" and "state change" mean for an MR

Facts:
- Both MR lists are `state=opened`. `GitlabItem` has no state field; `draft` is a boolean; closed/merged MRs reach the app only through the optional recently-closed section (assigned MRs only, `closedDays`).
- A hidden record is matched to the open list by id; a record without a listed item becomes absent (`MarkAbsent`) and is pruned after 30 days. A merged or closed MR therefore leaves the list and does not return unless reopened (then `Returned`). Records hold no title/URL (AGENTS.md), so a row for an absent MR cannot be drawn from the record alone.
- GitLab issues have the same structure; their "state" is the scoped-label fingerprint and a close/reopen is detected only as leave + return.

Options for the plan (the user's rule says a state change brings the MR back):
- **O1 (recommended default, no extra call): "state change" = the MR leaves the open lists and later returns (reopened).** MR fingerprint is empty (like GitHub: `status_fingerprint()` returns `Vec::new()`, so labels never bring an MR back; this matches "only state or comment"). A hidden MR that is merged or closed disappears like any closed MR; its record is pruned after 30 days; with `closedDays` on it shows in "Ostatnio zamknięte". Consistent with S-01 and issue hiding, cheapest. Drawback: a merge or close of a hidden MR is not shown as "Zmienione".
- **O2: also surface a merge/close.** When a hidden MR is in neither open list, read its state with a second new read-only call `glab api projects/<pid>/merge_requests/<iid>` (parsed with the existing `RawItem`, which has `state`, `merged_at`, `closed_at`; the stored `project_id`/`iid` make the call possible without the list) and show it as a visible row marked "Zmienione" (reason `status`) with a state tag. Costs: a second `CliCall` and guard shape, a state field on the item, a place for a non-open MR in the assigned table, and one call per absent hidden MR per round until acknowledged. The only way to honour the literal reading for merges.
- **O3: use system notes** ("merged"/"closed"/"reopened") from the same notes call. Not recommended: it works only while the MR is listed (merged MRs are not), and reading note bodies or `system_note_metadata` is fragile and unverified.
- Draft <-> ready is not a state change by default (not in the user's rule). If wanted, the fingerprint would be `["draft"]` or `[]`, which `status_changed` already supports.

## 8. Dedupe, placement and storage choices (agent defaults for the plan to confirm)

- **One record per global id**: `scope` = `config.host.as_str()` (lowercase), `kind='mergeRequest'`, `project_id`/`iid` from the item. The hide command finds the id (kind `mergeRequest`) in `merge_requests`, then `review_requests`; the lists are disjoint after `split_review_requests`. If an MR changes section while hidden it stays hidden.
- **Partition both lists by the same records**: hidden MRs from either list go into one new list `hidden_merge_requests` (TS `hiddenMergeRequests`), each keeping its `reviewRequested` flag. Default placement: hidden MRs show in the main table as dimmed rows after the visible ones (with the existing "Do review" tag when `reviewRequested`), toggled by the one "Pokaż ukryte (n)" where n = hidden issues + hidden MRs; the "Do review" panel then shows visible review MRs only. Alternative: two lists with hidden rows inside each panel (more fields, `FilteredOut` entries and tests). The "Typ" switch already filters rows by kind.
- A resurfaced MR returns to its own section carrying `changed` ("Zmienione"); "OK, zauważone" dismisses it; same three buttons and icons as issues.
- The round reads rows with `list_items(store, Gitlab, MergeRequest)` and keeps only rows whose scope equals the configured host (the table also holds GitHub rows and other hosts). Hidden state is keyed by host only, not user, as for issues.

## 9. Risks and overlap with S-03

- **Shared files (S-03 `github-new-and-notify` takes migration v16):** `src-tauri/src/cli/mod.rs` and `src-tauri/src/bin/fake_cli.rs` (S-07 adds a call and routes; S-03 should add none; the counters `VARIANT_COUNT`/`EXAMPLE_COUNT` and the `seen` array are conflict hotspots if it does); `src-tauri/src/lib.rs` (append command registrations only); `AGENTS.md` Hard Rules app-data sentence (both slices edit the same long line; S-07 changes only the hidden-item snapshot part: add "GitLab merge requests by host and global id" and extend "(GitLab scoped labels, empty for GitHub)" to cover merge requests); `src-tauri/src/hidden_issues/` (S-07 only); `new_assignments/` and GitLab seen keys (S-03 may generalise; S-07 touches only `all_items` and `mark_fresh`); `store/schema.rs` (S-07 none). The PRD gets at most a one-line note (roadmap Open Question 2), no FR numbers.
- **Behaviour risks:** (a) without `gitlab.user` the user's own MR comments resurface a hidden MR (same as issues; the existing notice covers it); (b) MR `updated_at` churn means more notes calls than issues; (c) id collision between issue and MR ids in code matching by bare id (`busy` set in `useGitlab.ts`, `find` helpers); (d) the existing test `act_on_issue_refuses_an_mr_or_an_unknown_id` (`gitlab_refresh.rs:~1364`) encodes "MRs are refused" and must be rewritten; (e) a failed round must keep hidden MRs hidden and show `hiddenError`, never an empty list (`reshape_kept` and the unpartitioned fallback must cover MRs); (f) the "To do" reconcile must not tick a hidden MR's entry; (g) logs: kinds and counts only, never a host, reference, id or login; (h) the MR notes response format was not verified against a live GitLab.
- **Unchanged:** the `hidden_issues` table and GitLab issue behaviour, `ChangeReason`, `SETTLE_MS`, `PRUNE_AFTER_MS`.

## Open questions (for `/10x-plan`; defaults noted)

2. Is draft <-> ready a state change? Default: no.
3. Placement of hidden review-only MRs: main table (default) vs inside "Do review".
